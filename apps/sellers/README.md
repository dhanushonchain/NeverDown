# @neverdown/sellers — x402 RPC merchant (C1)

Chunk plan: [docs/BUILD-CHUNKS.md](../../docs/BUILD-CHUNKS.md#c1--x402-seller-returns-http-402).

A small HTTP merchant that sells JSON-RPC access on **Hedera testnet** using the
[x402](https://github.com/x402-foundation/x402) payment protocol (v2, `exact` scheme).
NeverDown's Supreme Agent will later buy capacity from merchants like this one.

**C1 scope:** the merchant issues a real, standards-compliant payment challenge (HTTP 402)
for every unauthenticated RPC call and never runs the RPC operation without payment.
Paying, verifying, and settling a payment from a buyer is **C2**, not C1.

## Architecture
  
```
client ──POST /rpc──▶ express.json (16 kB limit)
                     └─▶ JSON-RPC shape + method allowlist   (400, no 402, no upstream)
                         └─▶ x402 paymentMiddleware          (402 challenge if unpaid)
                             └─▶ handler
                                 ├─ mock mode:    deterministic local responses
                                 └─ upstream mode: fixed RPC_UPSTREAM_URL (paid calls only)
GET /health ──▶ public
```

- `src/config.ts` — validates all environment variables at startup (fails fast).
- `src/rpc.ts` — JSON-RPC validation, mock chain responses, bounded upstream forwarder.
- `src/app.ts` — Express app; wires the official `@x402/*` packages.
- `src/server.ts` — entry point.

### Official packages used

| Package | Version | Role |
|---|---|---|
| `@x402/core` | 2.30.0 | `x402ResourceServer`, `HTTPFacilitatorClient` |
| `@x402/hedera` | 2.30.0 | `ExactHederaScheme` (`@x402/hedera/exact/server`) |
| `@x402/express` | 2.30.0 | `paymentMiddleware` (challenge + verify + settle flow) |
| `@x402/paywall` | 2.30.0 | Peer dependency of `@x402/express` |
| `express` | ^5.1 | HTTP server |

The payment challenge is generated by the SDK, not hand-built.

## Endpoints

### `GET /health` (public)

```json
{ "status": "ok", "service": "neverdown-rpc-seller", "network": "hedera:testnet" }
```

### `POST /rpc` (x402-protected)

Accepts one JSON-RPC 2.0 object. Allowed methods: `eth_chainId`, `eth_blockNumber`,
`net_version`, and `eth_getBlockByNumber` (only `["latest", false]`). Other methods take `[]`. Body limit: 16 kB.

### `POST /probe` (public, bounded)

Supports `eth_chainId`, `eth_blockNumber`, and `eth_getBlockByNumber` for capability checks. The seller caps probes at 120 per minute per process; additional requests receive HTTP 429.

### `POST /rpc-pack` (x402-protected)

A successful Hedera x402 settlement returns a bearer token for 100 `/rpc` reads within 15 minutes. The token remains inactive until settlement succeeds. The seller stores only its SHA-256 hash and remaining allowance in SQLite. Send `Authorization: Bearer <token>` with each RPC request. The existing per-request x402 `/rpc` purchase remains available for `pnpm pay:once`.

| Situation | Response |
|---|---|
| Malformed JSON, batch array, wrong `jsonrpc`, bad `id`, disallowed method, non-empty `params` | `400` JSON-RPC error (`-32700` / `-32600` / `-32601` / `-32602`). No challenge, no upstream call. |
| Body over 16 kB | `413` |
| Valid request, no payment | `402 Payment Required` with a `PAYMENT-REQUIRED` header (the x402 challenge). |
| Valid request, paid (C2+) | Executes the RPC operation and returns the result with settlement metadata. |
| Upstream failure (upstream mode, paid) | `502` JSON-RPC error `-32603`, with no upstream details echoed. |

## Environment variables

Copy the Sellers section of `.env.example` to `.env` at the repo root.

| Variable | Default | Meaning |
|---|---|---|
| `SELLER_PORT` | `4001` | Listen port (1–65535). |
| `SELLER_ENTITLEMENT_DB_PATH` | `neverdown-seller.sqlite` | SQLite file for settled RPC entitlements. Set a persistent private path; use `:memory:` only in tests. |
| `HEDERA_NETWORK` | `testnet` | Must be `testnet` in C1. |
| `HEDERA_MERCHANT_ACCOUNT_ID` | — (required) | Your Hedera testnet account that receives payments, format `0.0.N`. This is a public account id, not a key. |
| `HEDERA_X402_ASSET_ID` | `0.0.0` | Price asset. `0.0.0` = HBAR. Otherwise an HTS token id. |
| `HEDERA_X402_PRICE_SMALLEST_UNITS` | `10000` | Integer price in smallest units. For HBAR that is tinybars: `10000` = 0.0001 HBAR. |
| `X402_FACILITATOR_URL` | `https://x402.org/facilitator` | Facilitator used for `/supported`, `/verify`, `/settle`. Must be `https` (`http` allowed only for localhost). No credentials in the URL. |
| `RPC_MODE` | `mock` | `mock` or `upstream`. |
| `RPC_UPSTREAM_URL` | — | Required when `RPC_MODE=upstream`. Fixed `https` URL. Clients cannot choose it. |

Invalid or missing values stop the process at startup with a message naming the variable
(values are never printed).

```

Production-style run after a build:

```

## Mock vs upstream mode

- **`RPC_MODE=mock`** (default): answers from a fixed local chain. Values: `eth_chainId`
  `0x7a69` (31337, the Hardhat/Anvil default), `net_version` `"31337"`, `eth_blockNumber`
  `0x10`. These are not a real network.
- **`RPC_MODE=upstream`**: paid calls are forwarded to `RPC_UPSTREAM_URL`. Only the
  validated `method` and `id` are sent, with `params: []`. The forwarder uses a 10 s
  timeout, `redirect: "error"`, and a 1 MB response cap. Upstream error bodies and
  payment headers are never sent back to the client.

In C1, no request reaches either branch without payment, so upstream mode is exercised
only by unit tests of the forwarder.

## Verify it (reproduce the C1 gate)

Start the server (see above), then:

```bash
curl -i \
  -X POST http://localhost:4001/rpc \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_blockNumber","params":[]}'
```

Expected:

```text
HTTP/1.1 402 Payment Required
PAYMENT-REQUIRED: eyJ4NDAy...
```

The body is `{"error":"Payment required"}`. The challenge is in the `PAYMENT-REQUIRED` header.

Decode it:

```bash
curl -s -D - -o /dev/null -X POST http://localhost:4001/rpc \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_blockNumber","params":[]}' \
  | tr -d '\r' | grep -i '^payment-required' | cut -d' ' -f2- \
  | python3 -c "import base64,json,sys; print(json.dumps(json.loads(base64.b64decode(sys.stdin.read().strip())),indent=2))"
```

### Challenge structure

```json
{
  "x402Version": 2,
  "error": "Payment required",
  "resource": {
    "url": "http://localhost:4001/rpc",
    "description": "Paid JSON-RPC access to a NeverDown RPC endpoint",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "hedera:testnet",
      "amount": "10000",
      "asset": "0.0.0",
      "payTo": "<HEDERA_MERCHANT_ACCOUNT_ID>",
      "maxTimeoutSeconds": 60,
      "extra": { "feePayer": "<fee payer from the facilitator /supported>" }
    }
  ]
}
```

`feePayer` comes from the facilitator's `/supported` response, not from local config.
The x402.org facilitator currently advertises `0.0.9185802` for `hedera:testnet`. Check
it yourself:

```bash
curl -s https://x402.org/facilitator/supported | python3 -m json.tool | grep -A3 hedera:testnet
```

## Security assumptions

- **No payment bypass.** Access depends only on the x402 middleware's verification. There are no `isPaid` flags, bypass headers, or mock payments. `X-PAYMENT`, `PAYMENT-SIGNATURE`, and similar headers are ignored unless the facilitator verifies them (covered by Test G).
- **Unpaid requests never execute.** The handler sits behind the middleware (Tests D, E).
- **Fixed upstream (SSRF).** The upstream URL comes only from configuration. Clients cannot supply URLs. Redirects are refused.
- **Secrets.** The merchant needs only a public account id. No private keys are read or stored. `.env` is git-ignored. Do not put keys in `.env.example`.
- **Money.** Amounts are integer strings in smallest units. There is no floating-point arithmetic.
- **Logging.** Errors log only exception names and HTTP status codes, not request bodies or headers. The x402 library itself logs a stack trace when a `PAYMENT-SIGNATURE` header fails to decode. That trace does not include the payment payload.
- **Facilitator trust.** The facilitator decides whether a payment is valid. In C1 it is never called for a settlement. The default is the official x402.org facilitator. Use a facilitator you trust, and keep the URL https.

## C1 limitations

- **No real payment is accepted or settled.** Paid requests are not exercised end-to-end in C1.
- **`HEDERA_MERCHANT_ACCOUNT_ID` must be a real testnet account you control** before anyone pays you. Local examples may use placeholders for challenge-shape checks only.
- **Mainnet is not supported.** `HEDERA_NETWORK` must be `testnet`.
- **Only four RPC methods** are allowed. Batch requests are rejected.
- **Startup depends on the facilitator.** The first request (and startup sync) calls `/supported` to obtain the fee payer. If the facilitator is unreachable, requests return a facilitator error, not a challenge.
- **Unpaid body is minimal.** The challenge is in the header. The body is `{"error":"Payment required"}`.
- **Public probes are capped per seller process.** There is no distributed rate limiter or per-caller accounting. Paid entitlements have an expiry and request allowance.

## What C2 adds

Buyer lives in `@neverdown/core` + `scripts/pay-once.ts` (see [docs/C2-PAY-ONCE.md](../../docs/C2-PAY-ONCE.md)).

1. Set `HEDERA_SPEND_ID` + `HEDERA_SPEND_KEY` in root `.env` (funded testnet account).
2. Start this merchant: `pnpm --filter @neverdown/sellers dev`
3. Pay once: `pnpm pay:once`

That script:

- `POST /rpc` unpaid → reads `PAYMENT-REQUIRED`
- Signs Hedera exact `cryptoTransfer` via `@x402/hedera` + `@x402/core` HTTP client
- Retries with `PAYMENT-SIGNATURE`
- Prints Hedera `transactionId` + HashScan URL (live settle through the facilitator)

Hermetic buyer tests (mocked fetch): `pnpm --filter @neverdown/core test`.  
Seller C1 tests must stay green: `pnpm --filter @neverdown/sellers test`.

## What C3 adds

C3 wraps C2 behind **PolicyEngine** + **HCS** audit (`pnpm policy:smoke`). Allowlist / budget / payTo are checked **before** any x402 sign; PAY and DENY both land on a Hedera topic. See [docs/C3-POLICY-HCS.md](../../docs/C3-POLICY-HCS.md).

Policy checks, Arkiv discovery, ENS allowlists, HCS audit logging, and provider failover are later chunks.
